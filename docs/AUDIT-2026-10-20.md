# Security and UI follow-up — 2026-10-20

Security decision: **Do not launch yet** for public real-money operation.
Risk level: **High for financial launch until funded execution/recovery and deployed-host acceptance are observed**. The confirmed HTTP issues below are medium severity and have been fixed locally; this is not a newly discovered wallet takeover.

## Scope and trust boundaries

Reviewed owned FastAPI/Next.js sources, wallet challenge/session and network isolation, attributed strategies, project-public projection, author settlement/payment boundaries, request admission, client request lifecycles and deployment templates. Untrusted browsers/models must never supply capital, ownership or transfer permission. Separate financial processes remain explicitly disabled by default. No third-party service was attacked and no financial request, deployment or paid model call was performed.

## Confirmed findings

1. **Medium — OWASP A04, request capacity bypass during body upload — fixed.** `http_boundary.py` previously counted active requests only after assembling the request body. Slow POSTs could accumulate outside the eight-per-peer/128-global application limits until the body timeout. Capacity is now reserved before the first body chunk and released in `finally`, including cancellation, refusal and timeout. The regression holds eight unfinished uploads, verifies that a ninth is rejected without reading its body, and verifies subsequent recovery.
2. **Medium — OWASP A04, anonymous exchange-request amplification — fixed.** Public account lookups issued at least three upstream reads per call without a rate budget; changing wallet addresses/networks allowed repeated consumption of the server's exchange quota. The application now persists a shared 60-request/minute budget and ten-request/minute peer budget across the selected account/preview/inspection endpoints. Switching networks or addresses cannot reset it; exhausted requests return 429/Retry-After before upstream reads. In-process financial runners and recovery are outside this HTTP budget. This bounds exchange amplification, not every form of distributed denial of service.
3. **UI reliability — stale data after a stalled request — fixed in the UI substage.** Main-page requests had no deadline and a stalled request could hold the refresh lock indefinitely. Requests now have a 15-second deadline, an abortable component lifetime and per-request identity checks; public values clear on failure. Unavailable queues/journals show an unknown state rather than a false zero. Account lookups have deadlines, and report/identity changes clear previous report data. Financial authority is unchanged.

## Evidence and limits

- Full backend regression: **536 passed**, including 23 focused HTTP-boundary/admission cases. The existing upstream Starlette/httpx deprecation remains.
- `npm audit --omit=dev`: no listed production vulnerabilities. OSV's batch API: no advisories returned for the **64 exact Python lockfile pins** on this date. The local `pip_audit` module was unavailable, so this is an explicit OSV lookup, not a claimed pip-audit run. Dependency locks were not changed.
- A redacted scan of **198 tracked non-test text files** found no provider-key/PEM/literal private-key leads; no non-example environment files are tracked. Known public test vectors are excluded. This is a bounded current-tree scan, not a full Git-history or general secret-detection certification. Ignored runtime key files were not read or printed.
- Existing owner/network separation, replay protection, Decimal accounting, payout caps and unknown-command recovery tests remain passing. No auth bypass, XSS or secret disclosure was confirmed in this pass; this is not proof that none exist.
- UI verification: production build and 72 client tests pass. A local API fixture held responses for 40 seconds; the browser entered the bounded error state instead of remaining locked, and normal API restart restored the market feed. All four public tabs were checked at actual 320/375/414/768 widths with no page overflow or clipped buttons. Wallet-extension signatures and authenticated account switching were not exercised against a real wallet.
- `/operator` is a separate presentation surface, not authentication. Its financial writes still require server-side operator credentials. Restrict operational routes at the deployment boundary where appropriate; moving a menu item does not secure a route.

## Product/UI follow-up

The public tank currently projects registered mainnet execution journals. Genuine pre-execution research discussion is a separate feed integration: research can be inspected in Research, but it should not be represented as an executed project trade or populated with synthetic activity. The replacement interface must preserve that distinction when it is connected.

An isolated [agent interface study](AGENT-INTERFACE-CONCEPT.html) and [three-direction proposal](AGENT-INTERFACE-PROPOSAL.md) were prepared. The recommended compact committee makes each role/status/rationale visible and pins the final verdict; alternatives are a process rail and a live notebook. Four illustrative states and mobile/desktop layouts were checked. No new agent visual was installed in the main application.

## Remaining work before financial launch

Observe actual owner-controlled exchange permissions, fills/stops/revocation, payout/uncertainty recovery and capital reconciliation. Validate the container/HTTPS/proxy boundary and off-machine restore on a working deployment host, and obtain independent financial/security review. Local mocks, passing tests and public-market reads do not establish these external acceptance results. The Solana mint/funded treasury are still separate configuration.
