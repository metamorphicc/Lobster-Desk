# Explicit user financial execution

Stages 9.3a–c add explicit **testnet and mainnet** paths separate from the locked offline rehearsal. It does not turn sign-in, downloaded plans or `Lobster Desk Local Intent` signatures into trading authority. The new trade signature uses the distinct EIP-712 domain **Lobster Desk Execution Consent**, binding owner, exact private plan hash, dedicated API wallet, builder, fee and a short queue deadline. The saved plan binds quantity, price, direction, leverage, protections and current reviews. The existing rehearsal remains unconditionally locked.

## Separation of responsibilities

- The API uses the authenticated session only to identify the owner. Financial job creation/proof acceptance additionally requires `USER_TESTNET_FINANCIAL_ENABLED=true`; default is false. A valid new owner signature is required for each SDK permission or exact trade plan.
- SDK `approveAgent`, `approveBuilderFee` and zero-fee builder revocation jobs are immutable, owner/profile bound and share the durable serialized main-wallet nonce sequence. The SDK permissions themselves persist until revoked: the 30-second local queue deadline is not an on-chain permission expiry.
- `POST /api/v1/users/testnet/financial/jobs` prepares an idempotent job (`kind`: `agent`, `builder`, `revoke_builder`, `trade`; trade also supplies `plan_id`). `POST .../{id}/proof` verifies the exact owner signature and queues it. These routes never call `/exchange`.
- `GET /api/v1/users/testnet/financial` and `.../jobs/{id}` are private owner views. Proofs are redacted. The context reads only that owner's canonical execution journal and exposes no private keys.
- `npm run users:execution` inspects configuration without HTTP or financial dispatch. The separate process alone reads ignored `.env.users`, mapping each registered main public address to its dedicated API-wallet private key. Main-wallet private keys must never be put in that map. Public profiles are registered through the existing protected operator profile route; user/agent/builder roles cannot overlap.

## Opt-in runner

Copy `.env.users.example` to `.env.users`, register matching public profiles, configure the application's builder and `USER_TESTNET_EXECUTION_ROOT` (default `data/users-financial`). Explicit `USER_EXECUTION_ENABLED=true`, `npm run users:execution -- --run --arm` and API financial enablement are required for admission; source must be `hyperliquid-testnet`. Merely setting a model API key enables none of this. The API process never imports the key-map settings.

Each owner/agent pair has one journal and OS lease. Before entry, the inherited coded controls refresh account scope, builder eligibility/current approval, agent approval, account fees, cash-flow-neutral daily loss/drawdown references and exact user quantity/limit/expiry. Builder fees appear only on entry. Permission commands are claimed before HTTP and never automatically submitted twice. A timeout remains uncertain even if the current permission already matches: that observation cannot prove an old signed command will not arrive later. Uncertainty blocks new permissions and entries until reviewed. No automatic command reset endpoint exists.

The runner reconciles existing owned exposure before new jobs. Recovery rebuilds from the execution journal, independent of expired model reviews/previews, using a signer that **cannot enter or change leverage**. It refreshes funding/cash-flow risk references; accounting failure can trigger an owned reduce-only exit without allowing an entry. Actual fills determine stop size. Rejected/expired entries, fee revocation and uncertain commands cannot silently replay a trade. A cross-database interruption after proof claim but before staging needs inspection/fresh consent, not a second claim.

The runner remains opt-in for risk reduction after entry admission is disabled. Stopping all signer processes also stops active reconciliation; exchange-native protection remains on the exchange and must be checked by the owner. Revoking the API wallet can remove the runner's ability to close; the main wallet must then manage exposure directly.

All financial HTTP uses in-memory fixtures/public unfunded key vectors. No real wallet prompt, permission, funded order or builder fee collection was observed. Original 27 intent/orchestration cases still pass.

The browser workbench now provides explicit review/sign buttons for the registered API wallet, builder fee, fee revocation and exact private trade plan. It uses only `eth_signTypedData_v4` after strict validation; connecting, viewing a public account, sign-in and downloading an offline plan do not trigger financial signing. Wallet/account/network changes and expired queue deadlines discard pending proofs. Context polling and a private exchange journal distinguish queued consent from observed execution. No real extension prompt was used during development. The frontend suite has 58 cases, including Python-generated SDK fixtures, financial payload substitution refusal and account-change races. TypeScript/production build and eight labelled actual React state previews at 320/375/414/768 pass with no horizontal overflow. The live Treasury view also passed these widths and shows unconfigured/zero actual receipt states honestly.

The complete backend suite after these changes passes: **454 tests**. A legacy network-error wording assertion found during the full run was fixed to identify the required network explicitly; the full suite was then rerun successfully. No wallet or financial endpoint was exercised against a real external service.

User-owned mainnet code is implemented separately; funded acceptance remains open. Testnet routes and signatures cannot authorize mainnet execution. `.env.users` and its contents are ignored and excluded from source packaging; include all canonical journals in recovery inventory, then reconcile exchange state before resuming after a restore.

## Mainnet configuration and domain isolation

Mainnet uses `/api/v1/users/mainnet/…`, `USER_MAINNET_BUILDER_ADDRESS`, `USER_MAINNET_BUILDER_FEE_TENTHS_BPS=50`, `USER_MAINNET_FINANCIAL_ENABLED=false` and `USER_MAINNET_EXECUTION_ROOT=data/users-mainnet`. Both financial features default off. The operator registers a public profile at `POST /api/v1/operator/user-mainnet-profile` with `network: "mainnet"`. Mainnet requires a different dedicated API wallet from every registered testnet/user wallet; the same main public wallet can have separate profiles on both networks. Profiles are immutable.

Copy `.env.users-mainnet.example` to ignored `.env.users-mainnet`. `npm run users:execution -- --config .env.users-mainnet` only inspects that configuration. Explicit `--run --arm`, runner enablement and matching mainnet market source (`MARKET_SOURCE=hyperliquid`) are required for new entries. The runner alone reads that key map. Testnet uses its own `.env.users` file/root and source. All new writers are registered in the central recovery catalog before dispatch.

Sign-in uses a mainnet statement, chain 42161 (Arbitrum One) and `mainnet:preview` session. SDK permission actions use `Mainnet`/`0xa4b1`; trade consent uses `MainnetTradeIntent` and `mainnet-financial-consent-v1`. Explicit wallet methods validate those original domains before `eth_signTypedData_v4`; the default testnet methods still refuse them. Neither domain permits generic transfers. The browser has a distinct Mainnet tab and a real-funds notice. Public viewing requires no signature.

SQLite profiles, private previews, capital references/receipts and financial jobs use network-separated storage identities. This preserves existing testnet records and separate project capital ledgers without relabelling them. Canonical financial journal roots must differ. User account/profile/network/fee/plan identity is checked again before execution and recovery; no configurable arbitrary exchange destination is accepted.

Stage 9.3c verification: **495 Python tests and 69 client tests pass**, with TypeScript/production build, four responsive widths and eight labelled offline Mainnet review states. A real public mainnet `/info` lookup passed without wallet connection; it is read-only evidence, not execution acceptance. Real extension prompts, permissions, funded orders, builder receipts and recovery against the live exchange remain unobserved. Default execution remains paper.
