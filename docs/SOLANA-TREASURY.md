# Solana buyback and burn runner

The owner selected Solana. `npm run treasury` inspects configuration without HTTP or financial submission. Copy `.env.treasury.example` to ignored `.env.treasury`; enter the actual classic SPL mint, a dedicated Solana treasury wallet, Jupiter API credential and explicit USDC reserves. The Hyperliquid API wallet is a different key and cannot sign Solana operations. Missing mint, keys, reserves or enablement refuses dispatch. No token creation/issuance feature is included.

## Executable flow

1. Actual received fees / net project settlements enter the independent receipt book (see `REVENUE-INGESTION.md`). The 40/20/40 fee split and cumulative 50% net-profit entitlement still apply. Charity/team earmarks cannot be spent on buybacks.
2. Prepare an exact USDC purchase: `npm run treasury -- --buyback 10`. The tool checks fixed mainnet genesis, classic SPL mint/decimals, actual wallet USDC, current reserve-bounded entitlement and a Jupiter exact-input quote. This creates a local unsigned plan, not a financial submission.
3. Review the operation ID, then the owner may run `npm run treasury -- --dispatch OPERATION_ID --arm`. `SOLANA_ENABLED=true` is also required. Source implements this writer; it was never invoked against a real RPC during development. The transaction is built locally: bounded compute, idempotent project-token ATA creation and a decoded Jupiter route. Provider setup/tips/cleanup/opaque transaction blobs are never signed. Maximum input, minimum output, signer, source/destination accounts, slippage and zero platform fee are verified. Classic direct single-pool Raydium / Raydium CLMM / Raydium CPMM / Whirlpool routes are supported; unknown route versions, split/multihop routes, Token-2022 and native SOL are refused.
4. Signed bytes, signature and the sending claim persist before RPC submission. A timeout never generates another signature or blockhash; reconcile the existing signature with `npm run treasury -- --reconcile OPERATION_ID`. Unknown transactions keep the reservation. A missing finalized receipt, including an expired unobserved transaction, requires owner investigation; it is not automatically treated as safe to repeat.
5. Finalized evidence must contain the exact signed transaction, a valid treasury signature, successful execution, bounded network fee, exact USDC decrease and at least the minimum project-token increase. Only then do the spending receipt and received token lot commit atomically.
6. Prepare a burn with `npm run treasury -- --burn PURCHASE_ID`, then dispatch its operation ID with `--arm`. Locally constructed **SPL BurnChecked** consumes the full actual purchased quantity, including output above the quote minimum. Finalized transaction and token-balance reduction must match the unconsumed lot. A transfer to a sink address cannot satisfy this flow. SPL burn reduces total mint supply by token-program semantics; the tool does not infer circulating supply or a price effect.

`npm run treasury -- --run --arm` is a separate owner-enabled loop. It first reconciles existing transactions, then burns remaining purchased lots, then prepares a buyback when at least 5 USDC of eligible budget is available (default per-purchase maximum 25 USDC; configured absolute maximum 100). Default slippage is 50 bps, capped at 100. Prepared unsigned expired plans can be cancelled/replaced; signed uncertain transactions cannot. The process lease and immutable wallet/mint/network identity prevent concurrent local operation under one book. Separate machines/books using the same wallet are unsupported.

## Funding and evidence boundaries

The fixed RPC is `https://api.mainnet-beta.solana.com`, checked against the full mainnet genesis hash; Jupiter uses `https://api.jup.ag/swap/v1`. Public RPC rate limits/outages block progress. The classic API is used to inspect/build supported instructions rather than signing arbitrary provider transaction bytes. Provider protocol changes fail closed and require review.

Hyperliquid cash is **not automatically bridged** to Solana. The owner must fund the dedicated wallet with actual Solana USDC and SOL gas, recording cross-network principal movement once, never as new revenue. The code checks both the global entitlement and actual Solana token balance, so a Hyperliquid receipt alone cannot authorize spending absent Solana funds. An autonomous cross-chain bridge is not implemented. Network gas and ATA rent are paid in SOL, bounded separately and excluded from USDC buyback input; reconcile native-wallet costs as operating expenses using an explicit valuation policy before reporting net project profit.

`/api/v1/economics` includes a read-only `solana` operation/lot summary without loading signing keys or exposing signed bytes. Finality is an observation from a trusted fixed-host RPC, not independent consensus verification. Legacy receipt reports remain explicitly unverified. Preserve the treasury database in backups: it holds reservations, signatures, lots and journal events. Never restore an old snapshot and resume spending without reconciling all signatures and external activity.

## Verification

13 focused tests cover purchase → actual received amount → burn, restart, timeout/no duplicate submission, widened/malicious instructions, mainnet mismatch, changed profit entitlement, unarmed dispatch, balance mismatch and configuration. A LiteSVM test executes BurnChecked with the real SPL Token program and verifies both token-account amount and mint supply decrease. HTTP acceptance remains mocked; no actual swap/burn, token issuance, funded acceptance or bridge occurred. 72 combined treasury/revenue/book/distribution/release/API tests pass. The newly pinned `solders==0.29.0` and `jsonalias==0.1.1` bring the Python lock to 58 entries; all installed versions match, `pip check` succeeds, and the strict 2026-10-17 advisory lookup reports zero skipped/known-vulnerable packages.
